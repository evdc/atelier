## Context
`atelier-store` group-commits appends on a single writer thread. Subscriptions by exact stream use the
`events_by_stream(stream, seq)` index; prefix subscriptions (`p/<project>/`) range-scan on stream and then sort by
seq, which degrades as a project's history grows.

## Scope
- A `cargo bench`-free benchmark binary (`crates/atelier-store/examples/bench.rs`): append throughput (single and
  128 concurrent appenders), catch-up read speed for exact and prefix filters at 1M events, projection rebuild time.
- Record numbers in this ticket. If prefix catch-up from seq 1 over 100k events in one project exceeds 200 ms, fix it
  — e.g. a `project` column with an index on `(project, seq)`, populated at insert from the stream name — and
  record numbers again.

## Result
`cargo run --release -p atelier-store --example bench`. Load averages on the dev machine were 200-300 from other
sessions during these runs, so absolute numbers are noisy; read them as order-of-magnitude.

Dataset: 10 projects x 10 sessions x 10k events = 1M events, interleaved across streams. Catch-up pages are 500
events, as in `atelier-server`'s subscription loop.

| Measure | Before | After |
|---|---|---|
| Append, 1 appender, 1 event/call | 4,505 ev/s (first run) | 2,400-3,300 ev/s (noisy) |
| Append, 128 concurrent appenders | 15,171 ev/s | 12,300-14,600 ev/s |
| Load 1M events (projection v1) | 29.8 s | 39.9 s (load-dependent) |
| Projection rebuild, 1M events | 22.3 s | 7.9 s (load-dependent) |
| Catch-up exact stream, 10k of 1M | 45.9 ms | 30-63 ms |
| **Catch-up prefix `p/P0/`, 100k of 1M, from seq 1** | **714 ms** (worst page 151 ms) | **122 ms** (worst page 12 ms) |
| Catch-up prefix `p/`, 1M of 1M, from seq 1 | 3,554 ms (worst page 202 ms) | 857 ms (worst page 6 ms) |

The 714 ms prefix number was over the 200 ms bar, so the fix went in: `events.project` (the text between `p/` and the
next `/`, set at insert), an `events_by_project(project, seq)` index, and prefix queries of the form `p/<project>/`
read through it. Other prefixes keep the stream-range query. Existing logs get the column added and backfilled on open,
in one transaction.

Intermediate run, index without the planner hint: prefix `p/P0/` 508 ms. The hint (`INDEXED BY`) was added afterward
and the next run gave 122 ms, but that run was also under lower load, so the drop is not cleanly attributable to the
hint. The index itself is what removes the per-page scan-and-sort; the 1M-row EXPLAIN plan chose it even without the
hint in the sqlite CLI.

Remaining cost is per-row decoding (about 1-3 us per event), the same rate as the exact-stream read.
