## Context
This is the mesh half of DESIGN §11. Any session can tell any other something. The target gets it as a new turn
and replies, if it wants to, with its own `send`. Read §11.3 for the event, envelope, hops and UI decisions; this
ticket implements them.

Read first: AT-026's code; `supervisor.rs` (`send`, `wait_stopped`, `ensure_running`); `views/sessions.rs`;
`web/src/agents/claude.ts` (how `user.message` becomes a transcript item); `web/src/ui/` transcript items.

## Scope
- **Domain**: `AgentMessage { from: SessionId, text, mode: MessageMode (Tell|Ask), hops: u32, refs: Vec<Seq>,
  ask_id: Option<String> }`, kind `agent.message`. `refs` and `ask_id` are `#[serde(default)]`. `Ask` is used by
  AT-030; here it's always `Tell`.
- **Call**:
  - `session.send` with an `Actor::Agent` appends `AgentMessage` (in the target's stream, cause = the sender's
    triggering `cc.assistant` seq) instead of `UserMessage`.
  - The supervisor delivers it through the same path as `send`, but with the envelope from §11.3 as the text.
  - Factor delivery so both kinds share `ensure_running`.
- **Tool** `send { to, text, refs? }`:
  - `to` accepts an id or a unique id prefix (≥ 4 chars); ambiguity is an error that lists the matches.
  - The result is one line: "delivered to 7f3a (running — it will see this after its current turn)" or "(idle —
    woke it)".
  - Refusals (errors, with reasons): archived target (suggest `ask` with fork once AT-031 exists), sending to
    yourself, empty text, text over 16 KB, and the hop limit.
  - Pre-allowed.
- **Hops**:
  - The sessions projection stores `last_input_hops`: `user.message` → 0, `agent.message` → its `hops`. Bump the
    version.
  - A send computes `hops = sender.last_input_hops + 1` and is refused at > 6, with "hop limit reached: this
    conversation needs the person. Tell them in your reply."
- **Queueing**: deliver mid-turn messages straight to stdin (CC queues them; verify this in the spike or here, and
  note `queued_turn_count`). If CC doesn't queue reliably, queue in the supervisor and flush on `result`.
- **Web**:
  - `claude.ts` folds `agent.message` into a new item kind.
  - It renders as a card with a gold left hairline. The heading is *from "<sender title>"*, linking to the sender
    (title from the sessions view and live). The body is markdown, with refs as links to `#/s/<from>?at=<seq>`;
    the `at=` scroll can be a no-op until the AT-024 follow-up.
  - The envelope text is never shown raw.
  - In the sender's transcript, the `send` tool call renders as a compact line, *→ "<target title>"*, plus the
    first line of the text.
- No notification and no red: an agent message doesn't need the person.

## Notes (as built)
- **Queueing**: not verified against the real CLI (the spike was blocked here), so the supervisor queues. An
  agent message to a session whose turn is in progress is logged at once but written to stdin when that turn's
  `turn.ended` is logged, one per turn (`Proc.turn_active`/`queued`). A person's message still goes straight
  through. If the process dies first, queued messages are lost (the log keeps them as `agent.message`).
  Follow-up: if real CC queues reliably, this can go.
- Ids are UUIDv7, so sessions created together share a long prefix. The envelope and result lines carry the full
  id, and a prefix must be long enough to be unique.
- `agent.message` also appears in `read`/search documents (role `message`). `?at=<seq>` is parsed by the router
  but nothing scrolls to it yet.
- Not done: the "checked with the real CLI" item.
