## Context
`send` is fire-and-forget: the reply arrives as a later turn. Often an agent wants an answer *now*, inside its own
turn, like a function call: "B, what lock order did you settle on?" `ask` delivers the question like `send` (mode
`ask`), blocks the tool call until the target's turn that handled it ends, and returns the target's final text.
DESIGN §11.3.

This depends on what AT-026's spike found about long-running MCP calls. If CC times tool calls out at a few
minutes, `ask` has a server-side timeout below that and says so in its result.

## Scope
- **Tool** `ask { to, question, timeout_s? }`. `timeout_s` defaults to 600 and is capped below CC's tool timeout.
  - Appends `agent.message { mode: Ask, ask_id }`.
  - The envelope says: "Your final message this turn is returned to them as the answer. Keep it self-contained."
  - The handler parks on a `tokio::sync::oneshot` keyed by `ask_id`.
- **Resolution**: the supervisor watches the target's turns.
  - The turn that *consumed* the ask is the first `cc.result` after delivery that ends a turn begun after the
    `agent.message` seq.
  - The answer is that turn's last assistant `text` (all text blocks of the final `cc.assistant`), capped at 16 KB.
  - If the target errors, is stopped, or its turn ends with a pending permission it didn't get, return a clear
    error.
- **Waiting state**:
  - While parked, the asker shows "asking <target>…" in its header. This is derived: an unanswered `tool_use`
    named `mcp__atelier__ask`, so no new event.
  - Interrupting the asker cancels the wait. The question stays delivered, and the target's answer still lands in
    its own transcript.
- **Deadlock**: keep an in-memory wait-for graph `asker → target` of open asks. Refuse an ask that would close a
  cycle, naming the cycle. It's in memory because open asks die with the process anyway; at-most-once, like §10.5.
- **Restart**: open asks fail when atelierd restarts. The asker's tool call errors and the agent can retry. Don't
  try to resume them.
- Pre-allowed.
