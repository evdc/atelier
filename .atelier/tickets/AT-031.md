## Context
Asking a persistent agent costs it context: the Q&A stays in its window and it rots a little each time. CC can fork
a session with full memory (`--resume <native> --fork-session`; DESIGN §6). `ask { fork: true }` answers from a
throwaway fork. The target is never disturbed, can be mid-turn, and can be **archived**. Every finished session
becomes something you can still ask. DESIGN §11.4.

Read first: the driver's `Resume::Fork`, AT-030's code, and `views/sessions.rs`.

## Scope
- `ask { to, question, fork: true }`:
  1. Create a hidden child session: `parent = asker`, `SessionCreated` gains `#[serde(default)] fork_of:
     Option<SessionId>`. Its workspace is a read-only **share** of the target's worktree (AT-033), so the
     archive/pool rules keep the worktree alive while the fork runs. If the target's worktree is gone, use the
     project checkout, read-only.
  2. Start it with `Resume::Fork { native_id: target's, at: None }`, AT-033's read-only flags, plus a system append:
     "you are a fork answering one question; don't change files".
  3. Send the question, resolve as in AT-030, then archive the fork (no worktree to remove).
- The fork's events live in its own stream: auditable, and its cost counts toward the asker's tree (AT-032).
- Hidden: `SessionRow.hidden` (derived from `fork_of`) keeps it out of lists by default. The asker's transcript
  links to it ("answered by a fork of 'Fix WAL checkpoint' · open").
- A target that has never run, or has no `native_id`, errors with "nothing to fork yet".
- A fork while the target is mid-turn: verify on the real CLI that CC can fork a session whose process is live (it
  should, since it's a new process reading the jsonl, but the last turn may be partial). Write down what happens.
- `send` to an archived target: the refusal now suggests `ask` with `fork: true`.

## Out of scope
- Forking at a specific message (M5's fork UI).
- Keeping the fork alive for follow-ups (just ask again).
