## Context
A session is two independent choices: a **context** (fresh, or a fork of another session) and a **workspace**.
Today the workspace is either a new worktree from the project's HEAD or the project directory. This ticket lets a
session's workspace come from *another session*:

- **Share X's worktree, read-only.** The new session runs in X's directory and sees X's live, uncommitted edits.
  It's for code review, running X's tests, and investigating.
- **Branch from X.** The new session gets a fresh worktree at a *snapshot* of X's working tree, including
  uncommitted and untracked (non-ignored) files. X is never touched. It's for trying an alternative from where X
  is, splitting off a subtask, or reviewing a stable point while X keeps going.

The motivating flow is **build, then review**. A reviewer with a *fresh* context (so it doesn't share the builder's
blind spots) shares the builder's worktree read-only, reviews the diff against the builder's base, and reports
back. Later it re-checks the fixes, still remembering what it flagged.

Every pairing of context and workspace is a feature somewhere else:

| context | workspace | what it is |
|---|---|---|
| fresh | share X | reviewer (this ticket) |
| fresh | branch from X | parallel subtask / alternative (this ticket; `spawn`'s default in AT-029) |
| fork of X | share X | ask-a-fork (AT-031) |
| fork of X at m | branch from X's checkpoint at m | M5's "fork here" |

The snapshot helper is the same one M5's per-turn checkpoints need (`refs/atelier/…`, mockup step 6).

## Scope

### Domain (log-compatible: one new variant and optional fields only)
```rust
pub enum WorkspaceMode { Worktree, Direct, /// Another session's worktree, read-only.
                         Shared }
pub struct Workspace {
    pub mode: WorkspaceMode, pub path: String, pub branch: Option<String>, pub base: Option<String>,
    /// The session this workspace came from: the owner for `Shared`, the snapshot source for a branched `Worktree`.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub from: Option<SessionId>,
    /// For a branched `Worktree`, the snapshot commit it started from (also its `base`).
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub snapshot: Option<String>,
}
```
A `Shared` workspace copies the owner's `path`, `branch` and `base`, so the Changes view and diffs show the
owner's work against the owner's base, which is what a reviewer wants.

### Wire
`Call::SessionCreate` gains `#[serde(default)] from: Option<SessionId>`:
- `workspace: worktree` with `from` means branch from that session;
- `workspace: shared` requires `from`;
- `direct` with `from` is an error.

`from` must be in the same project and must not be archived. Sharing a `Shared` session resolves to its owner (no
chains). Sharing or branching from a `Direct` session is refused: there's no isolated worktree to share, so use the
project directory.

### Snapshot (`workspace::snapshot(ws) -> Result<String>`)
- Uses a temporary index, so X's index, files and HEAD are untouched:
  ```
  GIT_INDEX_FILE=<tmp> git read-tree HEAD
  GIT_INDEX_FILE=<tmp> git add -A                   # respects .gitignore
  tree=$(GIT_INDEX_FILE=<tmp> git write-tree)
  git commit-tree $tree -p HEAD -m "atelier: snapshot of <title> (<id>)"
  git update-ref refs/atelier/snap/<new-session-id> <commit>  # keeps it from being GC'd
  ```
- If the tree equals `HEAD^{tree}`, use `HEAD` itself and skip the commit and ref.
- Safe to run while X's agent is mid-turn: it reads the working tree, and at worst catches a half-written file.
  Don't block on X's turn. Do note "X was running when this was taken" in the new session's first message (below).
- The ref is deleted when the new session's worktree is released (`release`).

### `prepare` with a source
- **Branch from X**: same as `Worktree`, but `base` = the snapshot commit and the branch is created at it (pool
  claim or `worktree add`, as now). `seed` clones `target/`, `node_modules/` and `.venv` from **X's worktree**
  rather than the project checkout, since it's warmer and matches.
  - The new session's Changes view shows only its own work (base = snapshot).
  - The snapshot commit is on its branch. Merging back into X after X commits the same edits may conflict; the
    first-message note tells the agent this.
- **Share X**: no git work. Return X's workspace with `mode: Shared, from: X`.

### Read-only enforcement (honest, soft)
Sessions on a `Shared` workspace start with:
- `--disallowedTools Edit,Write,NotebookEdit`;
- a system append (shared with AT-026's mechanism, or the driver's `extra_args` if AT-026 isn't in yet): "You are
  in <X title>'s worktree, read-only. Don't modify tracked files; build and test output is fine."

Bash can still write. This is a convention backed by the permission mode, not a sandbox, and the ticket's Notes and
the UI copy must not claim otherwise. A shared session that changes tracked files shows up in X's Changes like any
edit. That's visible, not silent.

### One owner per worktree: archive and pool rules
- Archiving a **sharer** never touches the worktree.
- Archiving the **owner** while a non-archived sharer exists keeps the worktree. `Archived.kept` says "<Y> is
  reading this worktree". When the last sharer is later archived, and the owner is archived, run the owner's usual
  `unsafe_to_remove` → `release` path then, appending `WorkspaceRemoved` to the **owner's** stream.
- The pool already skips paths that any live session uses (`in_use`), so it needs no change. Add a test that pins
  this.
- `release` also deletes `refs/atelier/snap/<id>` for branched workspaces.

### Web
- **New-session form**: the workspace select gains "Share a session's worktree (read-only)…" and "Branch from a
  session…". Either one shows a session picker of this project's non-archived worktree sessions (title, status
  dot, branch).
- **"Review changes"** in the session header's menu, shown when the session has a worktree with changes. It opens the
  new-session form prefilled with workspace = share this session, title "Review: <title>", and the prompt:
  > Review the changes in this worktree (base `<base>`, branch `<branch>`) made by session "<title>". Read the diff
  > with `git diff <base>`, run the tests, and report problems by severity with file:line. Don't edit files.

  Once AT-028 lands, add "Send your findings to session <id> with `send`". Keep the template a const in one place
  so AT-029 and automations (§10.8) can reuse it.
- **Provenance lines** (gold, quiet):
  - a sharer's header: *reading "<X>"'s worktree*, linking to X;
  - a branched session's header: *branched from "<X>" at <short snapshot>*;
  - X's header: *read by "<Y>"* (from the sessions view: rows with `workspace.from == X`, mode shared, not
    archived).
- A sharer's Changes panel is titled "<X>'s changes".

## Acceptance
- [x] Unit tests (temp git repos, like the existing workspace tests):
      - the snapshot includes modified, staged and untracked non-ignored files and excludes ignored ones;
      - the source's index and HEAD are unchanged;
      - a clean tree returns HEAD;
      - branch-from produces a worktree whose base is the snapshot, with empty Changes;
      - `seed` copies from the source worktree;
      - `release` deletes the snap ref.
- [x] Unit/e2e tests for the rules:
      - share requires `from`, `direct` + `from` is refused, sharing a sharer resolves to the owner;
      - archiving the owner with a live sharer keeps the worktree, and archiving the sharer afterwards releases it
        and appends `WorkspaceRemoved` on the owner's stream;
      - the pool never claims a worktree a sharer uses.
- [x] e2e: the fake CLI records its args, and a shared session starts with `--disallowedTools Edit,Write,NotebookEdit`
      in the owner's directory.
- [x] vitest for any pure helper (e.g. the review prompt template, the "read by" derivation).
- [ ] Checked by hand with the real CLI: build in A; "Review changes" starts B in A's worktree; B finds a real issue;
      A fixes it; B re-checks in the same session.
- [x] `make check` and `make test` pass.

## Out of scope / follow-ups
- **Write-sharing** (two writers in one worktree, e.g. pairing). It needs a turn-level lock so two writers never run
  at once. Branch-from covers parallel writes for now.
- Snapshots at past messages (needs M5's per-turn checkpoints, which reuse `snapshot`).
- Sharing across projects.
- An automation that starts a reviewer when a session goes idle with changes: §10.8's row, once automations exist.
