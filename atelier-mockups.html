A window over the agents you have

The first version adds no new concepts. It lists every Claude Code and Codex session across your repos, shows which ones are waiting on you, and lets you start or resume one in its own worktree.

How it’s built

  • Tauri shell. Rust spawns claude or codex as child processes in a PTY, or headless with streaming JSON output where available.
  • History comes from the agents’ own transcript files, such as ~/.claude/projects/… and ~/.codex/sessions/…. A file watcher picks up sessions you started in a terminal too.
  • Your logins and subscriptions stay with the CLIs. Atelier never calls a model itself.
  • New sessions get a git worktree each, so several can run at once.

Tickets that hold sessions

A ticket is the unit of intent; sessions are attempts at it. One ticket can gather a research session, two build attempts and a fix-up, so the history of a change lives in one place.

How it’s built

  • A ticket is a Markdown file with front matter in .atelier/tickets/. Git is the sync and the history.
  • Starting from a ticket seeds the first prompt with its text and tags the session with the ticket ID.
  • An Atelier MCP server is added to each session, so the agent can tick a checkbox or add a note to its own ticket.
  • GitHub or Linear issues can be mirrored later. The file stays the source.

Everything gets an address

This is the step everything else rests on. Every thing (a code range, a session, one message, a ticket, a note, a commit) gets a URL. A link is just that URL written into any text. People and agents link the same way, and the app shows backlinks everywhere.

at://code/server/auth/session.ts#L20-41
at://code/server/auth/limits.ts#cooldown
at://session/cc-7f3c#m22
at://ticket/CP-52
at://note/decision-login-cooldown
at://commit/4be81a

How it’s built

  • Tauri registers the at:// scheme. An indexer scans .atelier/, code comments and session transcripts for those URLs and keeps a link table in SQLite. The table is a cache and can be rebuilt from the files.
  • Agents need no new tool to link. One paragraph in CLAUDE.md / AGENTS.md teaches them the scheme.
  • Code links store path, symbol, lines and a content fingerprint, so they re-resolve when code moves.

Pages the agent draws

Ask “what’s the request lifecycle?” and the agent writes a page: free HTML, whatever layout explains it best. The only rule is to link the boxes and sentences to what they describe, using the same addresses as step 2. Atelier makes those links work.

How it’s built

  • The agent writes .atelier/pages/request-lifecycle.html with an ordinary file write. A meta tag records the session and the question it came from.
  • Pages render in a sandboxed webview with no network. Atelier injects its stylesheet, so free-form pages still look like the rest of the app.
  • A small injected script turns at:// links into chips. A click opens the target beside the page, and any element with an id becomes addressable.
  • The same script marks boxes whose code changed since the page’s commit, and boxes a running session is touching.

How does this fit?

Once everything links, “the larger picture” becomes a query. Select any code, box, message or ticket and ask what is around it: pages that draw it, tickets that changed it, sessions that wrote it, open questions about it. Blame tells you who wrote a line; this tells you why.

How it’s built

  • Around this is a link-table query, widened by overlapping code ranges and by one hop through the call graph from a language server.
  • Why is this here starts with git blame to find the commit. Atelier knows which session made each commit, because sessions run in their own worktrees, and the matching edit tool call leads to the message that asked for it.
  • Trails are ordered lists of addresses with one sentence each, in .atelier/trails/. An agent can write one for any page: “walk me through it”.

Trust the agents, tend the garden

If agents make pages, notes and diagrams freely, the risk is clutter, not danger. So instead of gates, there is one place to look each morning. It holds questions that paused a run, short handoffs from finished sessions, new pages to keep or let fade, and pages whose code has moved.

How it’s built

  • Handoff notes come from a session-end hook that asks the agent for three lines: what’s done, what’s next, and what it’s unsure of.
  • A question is an address too (at://question/…). The run pauses, and your answer goes back into that session as a message.
  • Fading only hides things from lists. The file stays in git and keeps working as a link target.
  • “Out of date” compares the code ranges a page links to against the commit the page was drawn at.

Fork anywhere

Forking a conversation is only useful if the code forks with it. So Atelier quietly checkpoints the worktree after every turn that changes files. Any message becomes a place to branch from, either to try a different approach or to run several at once and compare.

How it’s built

  • After each file-changing turn (from a hook, or the file watcher), Atelier writes the worktree to a hidden ref using a temporary git index. The branch and staging area are left alone.
  • A fork is a new worktree at that ref, plus a session started in one of three ways. The chosen way is recorded, so you know how much the fork remembers.
  • Forks record their parent: forked_from: at://session/cc-7f3c#m14. The history view is drawn from those records.
  • Fan-out works the same way with a list of instructions, and the agents can differ.
# every file-changing turn
GIT_INDEX_FILE=$tmp git add -A
tree=$(GIT_INDEX_FILE=$tmp git write-tree)
git update-ref refs/atelier/cc-7f3c/m14 \
  $(git commit-tree $tree -p $prev -m m14)

7

Agents that start agents

There are two kinds of subagent. Some run inside the agent’s own loop, like Claude Code’s built-in subagents; Atelier can only watch those. Others an agent asks Atelier to start; those are full sessions in their own right, from any vendor, with their own workspace and budget. Both show up in one tree.

How it’s built

  • Observed: Atelier reads nested subagent transcripts where the agent writes them and draws them under their parent. You can’t steer them.
  • Orchestrated: the Atelier MCP server offers spawn. Atelier starts the child like any session, records its parent, and returns its result as the tool result. The parent can wait for it or keep going.
  • Workspaces: read-only is a checkout of the parent’s current checkpoint; worktree branches from it and returns a proposal; pages may write only to .atelier/pages.
  • Each child takes a slice of its parent’s budget. If a subtree runs over, it pauses and asks you.
  • Children inherit the policies. Something a person must approve stays flagged however many levels up it travels.

Proposals instead of pull requests

A pull request assumes a person wrote the code and another person reads all of it. Here an agent wrote it, and you read the parts that matter. So a session ends with a proposal. Atelier provides a fixed frame: doubts, evidence, parts, alternatives and a decision. Inside the frame, the agent writes the explanation freely, like any page.

How it’s built

  • A proposal is a file, .atelier/proposals/P-0412.md, plus a ref per version. Each part is its own commit, so accepting some parts is a cherry-pick and the rest go back to the session.
  • Revise sends your note into the original session as a message. It resumes from its last checkpoint, with its memory intact, and posts v2. Atelier shows what changed between versions with git range-diff.
  • Parts can change things that aren’t code: a page, a ticket, a note. You accept those the same way.
  • It is the same object at every level. A subagent proposes to its parent, a fork proposes back to its origin, and a session proposes to main.
  • Teams on GitHub can export a proposal as a PR. The reading guide and evidence go into the description.

Then: the pattern language ›

A pattern language for working with agents

In Christopher Alexander’s sense: each pattern names a recurring problem and a solution, and connects to larger patterns it helps complete and smaller ones that complete it. Asterisks mark confidence: ** fairly sure, * worth trying.

The language rests on three ideas. Everything is a plain file in the repo. Everything has an address. A link is just an address written into text. With those in place, people and agents use the same few moves (write a file, link to a thing, ask about a thing), and the app’s job shrinks to resolving addresses, showing backlinks, and noticing when things drift.

Teaching an agent the language

No plugin or fork. A paragraph in the repo’s agent instructions is enough, because every move is a file write or a URL.

# in CLAUDE.md and AGENTS.md
When you explain something, write a page to
.atelier/pages/<name>.html. Link every box and
claim to what it describes with at:// URLs,
e.g. at://code/path#symbol. Give boxes ids.
End each session with a 3-line handoff.

The optional helper tools

An MCP server, added to each session, makes the moves faster. The agent could do all of it with plain files, just less precisely.

around(url)      # neighbourhood of a thing
resolve(url)     # → file, lines, snippet
find(query)      # search all objects
ask(question)    # pause for a person
handoff(text)    # end-of-session note
spawn(task, …)    # start a child session
propose(parts)   # hand work back
